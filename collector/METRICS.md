# 단위경제 입력값 ← 수집 이벤트 대응표

`events` 시트의 열은 A~U 순서다.
A t · B vid · C sid · D ev · E dev · F role · G src · H screen · I act · J target · K intent · L reward · M withdraw · N secs · O form · P tx · Q grade · R gender · S org · T exp · U name

아래 수식은 **아직 실제 시트에서 돌려 보지 않았다.** 처음 쓸 때 몇 줄만 손으로 세어 값이 맞는지 확인한다.
N열(secs)이 숫자가 아니라 글자로 들어갔으면(셀이 왼쪽 정렬이면 글자) `MEDIAN` 이 오류를 내므로 `VALUE()` 로 감싼다.
`COUNTUNIQUE(FILTER(…))` 는 맞는 행이 하나도 없으면 0이 아니라 **1**을 돌려준다(FILTER 가 내는 #N/A 오류를 값 1개로 센다). 손으로 넣은 수식에서 1이 나오면 FILTER 결과가 비었는지 먼저 본다. 대시보드는 `LET(hits, FILTER(…), IF(ISERROR(INDEX(hits, 1)), 0, COUNTUNIQUE(hits)))` 로 센다.

## 먼저 할 일

1. 테스트 행을 뺀다. `src` 가 `claudetest` 인 행과 팀원이 시험 삼아 넣은 행은 계산에서 제외한다(수식에 `G2:G<>"claudetest"` 조건을 더하거나 별도 탭으로 옮긴다). 2026-11-06에 그때까지의 `claudetest` 행(배포 점검 4행, 동시 접속 시험 2,669행)을 모두 지웠다. 앞으로도 시험 행은 `src=claudetest` 로 넣고, 다 쓴 뒤 Apps Script 편집기에서 `clearTestRows` 를 실행해 지운다. 2026-11-04 이전의 시험 기록은 `events_old_1104` 탭에 그대로 남겨 두었다.
2. 동아리별로 나누려면 배포 주소에 `?src=club-이름` 을 붙여 나눠 준다(예: `…/?src=club-photo`). `src` 열에 그대로 남는다. `share-` 로 시작하는 이름은 앱의 공유 버튼이 쓰므로 손으로 나눠 주는 주소에는 쓰지 않는다(아래 "공유 퍼널").
3. 표본이 작으면 비율은 크게 흔들린다. 응답 30명이면 ±18%p, 100명이면 ±10%p 정도다. 비율을 보고서에 쓸 때는 "n=○○"를 같이 적는다.

## 입력값별 대응

| 모델 입력(v51) | 어디서 재나 | 계산 |
|---|---|---|
| 월 활성 부원 비율 52% | `page_view` 를 남긴 role=member 방문자(vid) ÷ 동아리 부원 수 | 부원 수는 앱 밖(총무에게 확인)에서 받아야 한다. 앱은 명단을 모른다 |
| 활성 부원 월 세션 2회 / 운영진 월 세션 12 | 방문자별 서로 다른 sid 수, role별 | `=COUNTUNIQUE(FILTER(C2:C, F2:F="member"))/COUNTUNIQUE(FILTER(B2:B, F2:F="member"))`. 기간이 한 달보다 짧으면 달 환산이 필요하다 |
| 세션당 광고 노출 1.5 | `ad_view` 행 수 ÷ 서로 다른 sid 수 | `=COUNTIF(D2:D,"ad_view")/COUNTUNIQUE(C2:C)`. 배너가 4장 돌아가므로 한 화면에서 최대 4번까지 센다(배너마다 화면당 한 번, 멈춰서 보인 것만). 모델의 1.5와 비교할 때는 이 점을 감안한다 |
| 광고 클릭률 0.3% | 배너 클릭 ÷ `ad_view`, 배너(target)별로도. 클릭은 2026-11-06부터 `ad_click`, 그 전에는 `ui_click`(act=`ad`)으로 남았다 | 전체 `=(COUNTIF(D2:D,"ad_click")+COUNTIFS(D2:D,"ui_click",I2:I,"ad"))/COUNTIF(D2:D,"ad_view")`, 배너별은 `J2:J="kb-insurance"` 처럼 target 조건을 세 곳에 모두 더한다. 배너 키: `kb-insurance`, `oliveyoung-sale`, `baemin-isaac-toast`, `spotify-afterparty` |
| 설문 소요 10분 | form=`survey:done` 행의 secs 중앙값 | `=MEDIAN(FILTER(N2:N, O2:O="survey:done"))` (초 단위). 샘플 설문이 15문항 약 5분짜리라 실제 일감의 10분과는 다르다 |
| 설문 완료율·이탈 구간 | form=`survey:A`~`E`, `done`, `out`, `quit-X` | 구간별 서로 다른 vid 수를 세어 A→B→…→done 으로 나눈다. `out` 은 대상 아님(1번 문항에서 탈락), `quit-X` 는 X구간에서 닫음 |
| 설문·일감 가입률 50% | perk_answer, target=`job-survey` 의 intent=yes 비율 | `=COUNTIFS(D2:D,"perk_answer",J2:J,"job-survey",K2:K,"yes")/COUNTIFS(D2:D,"perk_answer",J2:J,"job-survey")`. 말로 한 의향이라 실제보다 높게 나오기 쉽다 |
| 일감 참여 비율(UT·데이터·AI평가) | target=`job-ut` / `job-photo` / `job-eval` 의 intent=yes 비율 | 위와 같은 식에서 target만 바꾼다 |
| 일감 최소 보상(할 만한 금액) | 같은 target의 reward(원) 중앙값 | `=MEDIAN(FILTER(L2:L, D2:D="perk_answer", J2:J="job-ut"))` |
| 최소 인출 5,000원 | 첫 일감 답변의 withdraw(원) | `=MEDIAN(FILTER(M2:M, D2:D="perk_answer", LEFT(J2:J,4)="job-"))` |
| 쿠폰 사용률 1% | target=`food-*` 의 intent=yes 비율, reward(최소 할인 %) | 말로 한 의향이라 실제 사용률과는 다르다. 실제 사용률은 쿠폰을 실제로 발급해 봐야 안다 |
| 제휴 결제 비중 20% | target=`tr-pay` 의 reward(연 지출 중 %) 중앙값 | role=treasurer 답변만 들어온다 |
| 이동 행사 2회/년·18명 | target=`tr-insurance` 의 reward(명), withdraw(회) 중앙값 | 둘째 질문(연 몇 회)은 withdraw 열에 들어간다 |
| 통계 활용 동의율 70% | target=`tr-data` 의 intent=yes / maybe / no 비율 | 보고서에는 yes 만이 아니라 maybe 를 따로 적는다 |
| 방문 한 번의 체류 시간 | `session_time` 행의 secs. 같은 sid 안에서는 가장 큰 값 | `=QUERY(A:U,"select C, max(N) where D='session_time' group by C",1)` 결과의 평균·중앙값 |
| 화면별 머문 시간 | `screen_time` 의 secs | screen별 평균·중앙값. 한 사람의 탭별 시간은 아래 "한 사람의 탭별 체류 시간" |
| 방문자 대비 가입률 (대시보드 카드 없음, 2026-11-09에 뺌) | profile 행이 있는 vid ÷ **GA4 사용자 수** | 앱은 참여 정보를 입력하기 전의 기록을 메모리에만 두고 시트로 보내지 않는다. 그래서 시트에는 입력을 마친 사람만 있고, 시트 안에서만 나누면 늘 100%가 된다. 입력 창에서 나간 사람은 GA4에만 남으므로 분모는 GA4에서 가져온다 |
| 추천(공유) 유입·K | `share_click` → GA4 의 `app_src`=share-… 사용자 → src 가 share-… 인 profile vid | 아래 "공유 퍼널(추천 유입)". 모델(v51) CAC 시트에는 아직 추천 채널이 없다 |

## 대시보드 탭(시트 1면)

위 표의 값을 손으로 수식을 넣지 않고 한 장에서 보려면 `Dashboard.gs` 를 쓴다. 2026-11-07에 실제 시트에서 다시 만들어 숫자를 확인했다.

**2026-11-07 저녁 전 판의 숫자 주의:** 서로 다른 사람 수를 세는 수식이 맞는 행이 0건일 때 1을 냈다(위 `COUNTUNIQUE` 주의). 그래서 실제로는 0인 칸이 1로 보였다. 예를 들어 혜택 질문 응답자, 샘플 설문 단계별 도달(차트 포함), 유입 경로의 공유 링크 줄, 공유 퍼널의 공유한 사람·K, 피드백 반영 기능의 사람 수가 그랬다. 그 전에 대시보드에서 옮겨 적은 숫자 중 1이나 1에서 나온 비율(20%, 33% 등)은 고친 판으로 다시 확인한다. 1 이상인 진짜 값은 바뀌지 않았다.

1. 수집기를 붙인 같은 Apps Script 프로젝트에 파일(+) > 스크립트로 `Dashboard` 를 만들고 `Dashboard.gs` 내용을 붙여 넣는다.
2. 함수 `대시보드만들기` 를 한 번 실행한다. 맨 앞에 `대시보드` 탭이, 숨김으로 `_data` 탭(events 에서 시험용 src 와 제외할 이름의 방문자를 뺀 사본, 이름 열 없음)이 생긴다. 시트를 다시 열면 `QFlowz > 대시보드 새로 만들기` 메뉴가 생긴다.
3. 수집기 웹 앱은 다시 배포하지 않아도 된다. 숫자는 모두 수식이라 기록이 쌓이면 저절로 바뀐다. 스크립트를 다시 돌리는 것은 대시보드 모양을 바꿨을 때뿐이다.
4. 노란 칸은 직접 고친다: 제외할 src(기본 `claudetest`), 비교에 필요한 최소 표본(기본 10), 제외할 이름, 모델 가정 값. 다시 만들어도 이름표가 같으면 값이 그대로 옮겨진다.

**제외할 이름(2026-11-08~).** 팀원과 관리자처럼 테스터가 아닌 사람의 기록은 대시보드 계산에서 뺀다. 대시보드 C6 칸(쉼표로 구분)에 적힌 이름과 참여 정보(profile 행)의 이름이 같은 방문자(vid)의 **모든 행**을 `_data` 에서 뺀다. events 탭의 원본은 지우지 않는다.
- 저장소가 공개라 팀원 이름은 `Dashboard.gs` 에 적지 않고 시트의 C6 칸에만 둔다. 코드의 처음 값은 `관리자` 뿐이고, 대시보드를 다시 만들어도 C6 칸의 값은 그대로 옮겨진다. 대시보드 탭을 지웠다가 새로 만들면 C6에 팀원 이름을 다시 적는다.
- 2026-11-08에 C6에 관리자와 팀원 세 명의 이름을 넣고 다시 만들었다. 그때 events 358행 중 235행(방문자 코드 3개)이 빠졌고, 참여 정보를 입력한 사람은 5명에서 2명으로 줄었다. 그 전에 대시보드에서 옮겨 적은 참여자·방문 수는 팀원 기록이 섞인 값이다.
- 이름은 앞뒤 공백만 무시하고 글자가 같아야 맞는다("최 성혁"처럼 띄어 쓰면 다른 이름이다). 맨 아래 데이터 점검의 "이름으로 뺀 사람 (찾은 이름)"에서 실제로 걸린 이름을 확인하고, 빠진 사람이 있으면 events 탭 U열에 적힌 그대로 C6에 더한다.
- 한 사람이 휴대폰과 노트북을 썼다면 방문자 코드가 둘이지만, 둘 다 참여 정보를 입력하므로 둘 다 빠진다.
- GA4 보고서와 대시보드에 손으로 넣는 GA4 사용자 수에는 이름이 없어 이 사람들이 그대로 들어 있다. GA4 숫자를 쓸 때는 팀원 수만큼 들어 있을 수 있다고 적는다.

담긴 것: 한눈에 보기 카드 10개 → 차트 3개(설문 단계별 도달, 배너별 클릭률, 혜택 질문별 쓸 의향) → 모델 가정 vs 실측 표(가정의 ±10% 안이면 "비슷", n이 최소 표본보다 작으면 "표본 적음") → 혜택 질문 항목별 응답 → 샘플 설문 단계 → 배너별 → 유입 경로별(공유 링크는 총무·부원 두 줄로 합침) → 공유 퍼널(공유 → 유입 → 참여, 버튼 자리별, 공유 링크별) → 피드백 반영 기능(거래 줄 펼침, 접는 칸 열기, Q&A 알림 받음·누름, 질문·답변 수. 2026-11-07에 더함) → 개인화 A/B(그룹 a·b별 들어온 부원, 재알림 열람률, 참석 행사 의견 비율과 차이, 총무 줄: 들어온 총무·불일치 거래 펼침 비율·할 일 카드를 누른 총무. 2026-11-08에 더함) → 표본 구성 → 잴 수 없는 것 → 데이터 점검(열 순서, 숫자가 글자로 들어갔는지, 마지막 기록) → 화면별 머문 시간.

배너 클릭은 `ad_click`(2026-11-06부터)과 예전 `ui_click`(act=`ad`)을 더해 센다. 한 클릭은 둘 중 하나로만 남는다. 수집기는 2026-11-06 0시 28분에 `ad_click` 을 받는 버전 3으로 배포했다. 앱이 `ad_click` 을 보내는 것은 앱 변경이 main에 합쳐져 사이트에 배포된 뒤부터다.

**수집기 배포 기록:** 2026-11-07 20시 45분(한국 시간)에 버전 4로 배포했다. 이 버전부터 공유 기록(`share_click`), 확인 재알림(`nudge_view`·`nudge_click`), Q&A 알림(`noti_view`·`noti_click`)이 시트에 들어온다. 그 전에 쓰던 버전 3(2026-11-06 0시 28분)에는 이 다섯 가지가 없었다. 그래서 그 사이의 이 행들은 시트에 없고 GA4에만 있다. 공유 링크로 들어온 사람의 src 는 다른 행에 그대로 남아 있다. 배포 직후 `claudetest` 시험 행 두 개(`noti_view`·`noti_click`)가 들어오는 것을 확인했고, `clearTestRows` 로 지웠다.

처음 열었을 때 맨 위 "데이터 점검"이 정상인지 먼저 보고, events 에서 몇 줄을 손으로 세어 카드 숫자와 맞는지 확인한다.
`Code.gs` 의 열 배열을 바꾸면 `Dashboard.gs` 의 `기대열` 도 같이 고친다.

## 공유 퍼널(추천 유입)

2026-11-06에 앱에 공유 버튼을 넣었다. 모듈1 멘토링의 "네트워크 확장이 부족하다"는 지적에 답하는 추천 채널이고, CAC는 활성 동아리 1곳당이라 **다른 동아리 총무에게 퍼지는 공유**가 획득이다. 총무가 자기 부원을, 부원이 친구를 부르는 공유는 초대(참여 확대)로 따로 센다.

버튼 자리(form 열): 샘플 설문을 끝낸 화면 `share:survey`, 혜택 질문에 답을 보낸 뒤 `share:perk`, 총무 관리 화면 `share:admin`.
2026-11-07부터 공유 카드는 접거나 여러 단계를 거치지 않는 눈에 띄는 버튼 하나다. OS 공유 창이 있는 브라우저(휴대폰 대부분, 윈도 크롬·엣지)는 큰 '공유하기' 버튼(act=`native`, 카카오톡·인스타 DM 등으로 보냄)과 그 아래 작은 '글과 링크만 복사'(act=`copy`)가 보이고, 없는 브라우저는 큰 '글과 링크 복사하기'(act=`copy`) 하나만 보인다. 보낼 글은 숨겨 두었다가 복사가 막힌 브라우저에서만 펼친다. 복사는 소개 글과 링크를 함께 복사한다. 카카오 SDK 같은 외부 라이브러리는 쓰지 않는다. 버튼 자리·이벤트 값은 그대로라 대시보드는 바꿀 필요가 없다.

- 보낸 링크: `?src=share-t-<공유 코드>`(총무 화면에서 보냄) / `?src=share-m-<공유 코드>`(부원 화면에서 보냄). 공유 코드는 브라우저마다 처음 공유 카드를 볼 때 무작위로 만든 6자(localStorage `finpbl:share`)이고 방문자 코드(vid)와 별개다. 이름은 들어가지 않는다. 수집이 꺼진 브라우저(`?notrack=1`, '수집 안 함')는 코드 없이 `share-t` / `share-m` 만 붙인다. 동의를 철회하거나 수집을 끄면 공유 코드도 지운다.
- 누른 기록: `share_click` 행. act=`native`/`copy`, target=보낸 링크의 src 값(예: `share-t-k3f9a2`), form=`share:<자리>`, screen=누른 화면, src=보낸 사람 자신이 온 경로. GA에도 같은 이름으로 간다(app_act·app_target·app_form·app_screen 은 이미 등록한 측정기준이라 GA 설정을 바꿀 필요는 없다).
- 받은 사람: 링크로 들어오면 `?src` 가 그 브라우저에 기억되어 그 사람의 모든 행 src(G열)와 GA `app_src` 에 붙는다. 내 공유 코드가 붙은 링크를 내가 같은 브라우저에서 다시 열면 기억하지 않는다. 다른 브라우저(폰↔노트북)로 열면 새 사람으로 세어진다.
- '공유하기'는 공유 창을 연 순간에 센다. 창에서 앱을 고르면 이 화면이 뒤로 가서, 다 보낸 뒤에 세면 기록이 빠질 수 있기 때문이다. 그래서 공유 횟수는 "보낸 횟수"가 아니라 "보내려고 누른 횟수"이고, 실제로 보냈는지는 받은 사람의 유입으로 본다. 창을 그냥 닫은 경우도 한 번으로 세어진다.
- 보낸 글이나 받는 사람(카톡 대화방 등)은 알 수 없고 수집하지 않는다.

앱의 공유 버튼으로 보낸 것만 세므로, 팀원이 카톡 등으로 직접 보낸 건은 팀 발송 기록으로 더한다. 2026-11-07 20:45 이전 공유는 시트에 없어 GA4에서 본다.

GA4에서 '들어온 사람' 찾기: 탐색 > 자유 형식 > 측정기준 `app_src`(맞춤, 이벤트 범위), 측정항목 `총 사용자` > 필터 `app_src` 가 `share-t` 로 시작(부원 링크는 `share-m`). 기간은 대시보드에 넣을 기간과 맞춘다. 앱은 모든 이벤트에 app_src 를 붙이고, 참여 정보 입력 창에서 나간 사람의 page_view 도 GA에는 가므로 이 수가 공유 링크로 들어온 사람 전체다.

CAC 모델(`QFlowz_단위경제_v51.xlsx` CAC 시트)에 넣을 때
- 지금 K는 **사람 단위**다. CAC는 활성 동아리 1곳 단위라 그대로 넣지 않는다. 총무 링크로 들어와 총무 경험이 있다고 답한 사람(대시보드 H열)이 "추천으로 얻은 동아리 후보"다.
- 동아리 단위 K(유료로 얻은 동아리 1곳이 데려오는 동아리 수)를 K_c 라 하고 모든 세대가 같은 비율로 퍼진다고 보면, 유료로 얻은 1곳당 모두 1 ÷ (1 − K_c)곳이 된다. 그러면 혼합 CAC ≈ 채널 A CAC(93,285원) × (1 − K_c) 다(K_c < 1 일 때). 한 세대만 본다면 93,285 ÷ (1 + K_c).
- 표본이 작으면(공유로 들어온 사람 몇 명) K는 크게 흔들린다. 보고서에는 n 과 기간을 같이 적고, 팀원이 자기 링크를 다른 기기로 연 경우를 빼고 센다.

## 한 사람의 탭별 체류 시간

`screen_time` 행에 방문자 코드(vid)와 화면(screen)과 머문 초(secs)가 남으므로 가능하다. 화면 이름은 `m/ledger`(부원 거래 내역), `t/perks`(총무 혜택) 처럼 역할/탭이다.
이름은 참여 정보를 입력할 때 한 번 남는 `profile` 행(U열)에만 있으니, 이름으로 vid 를 찾은 뒤 그 vid 의 `screen_time` 을 합친다. 수식은 아직 실제 시트에서 돌려 보지 않았다.

1. 새 탭을 만들어 A1 에 찾을 이름을 적는다.
2. vid 찾기: `=INDEX(events!B2:B, MATCH(A1, events!U2:U, 0))` 를 B1 에 둔다.
3. 탭별 합계: `=QUERY(events!A:U, "select H, sum(N), count(N) where D='screen_time' and B='"&B1&"' group by H order by sum(N) desc label sum(N) '합계(초)', count(N) '횟수'", 1)`
4. 모든 사람을 한 표로: `=QUERY(events!A:U, "select B, sum(N) where D='screen_time' group by B pivot H", 1)` (행은 vid, 열은 화면)

알아 둘 점
- 시간은 탭이 화면에 보이는 동안만 센다. 다른 탭으로 가거나 화면이 꺼진 시간은 빠진다. 한 번에 최대 30분까지만 인정한다.
- vid 는 브라우저마다 따로 생기므로 같은 사람이 폰과 노트북을 쓰면 vid 가 둘이다. 이름으로 합친다.
- 이름은 새 `Code.gs` 를 배포한 뒤(2026-11-04 오후 10시 버전 2)에 입력한 사람부터만 저장된다. 그 전에 들어온 행에는 이름이 없다.
- 이 표에는 이름이 들어가므로 보고서에는 이름을 빼고 vid 나 "참여자 A" 같은 이름표로 바꿔 옮긴다.

## 광고 클릭률을 읽을 때

- 배너에는 "광고 자리 예시 · 실제 광고 아님"이 붙어 있고, 눌러도 어디로도 연결되지 않는다(토스트만 뜬다). 그래서 이 숫자는 실제 광고의 클릭률이 아니라 **"예시라고 알려 줬는데도 누른 사람의 비율"** 이다. 모델의 0.3%에 그대로 넣지 말고, 배너끼리 비교(어떤 소재가 더 눈길을 끄나)와 위치별 비교에 쓴다.
- 배너는 자동으로 5초마다 넘어가므로 노출 수는 "띠가 화면에 절반 이상 보이고, 배너가 멈춰 있을 때"만 센다. 지나가기만 한 배너, 탭이 가려진 동안의 배너는 세지 않는다.
- 배너 이미지의 광고주(KB손해보험·올리브영·배달의민족·이삭토스트·스포티파이)와 모델 얼굴은 실제 업체·인물의 것이다. 수업용 비공개 시연에서만 쓰고, 공개 배포 전에는 직접 만든 이미지로 바꾸거나 사용 허락을 받는다.

## 개인화 A/B (과업 ④): 개인화 화면 vs 개인화 없는 화면 (2026-11-08~)

**배정과 진행.** 테스터는 자기 그룹을 모른다. 진행자는 접속 주소로만 나눈다.

| `opinion_submit` | target=그룹, tx=거래 ID | 익명 의견(근거 확인/설명 요청)을 남김. 고른 의견은 보내지 않는다 |
| `ui_click` act=`nudgeclose` / `nudgeoff` / `clockskip` | target=그룹 | 닫기 / 다시 알리지 않기 / 시연용 시계를 마감 하루 전으로 옮김 |

그룹별 값(대시보드 "개인화 A/B" 구역에 같은 계산이 있다. 아래는 그룹 a, b는 `ab-a` 를 `ab-b` 로 바꾼다).
- 재알림 열람률: `=COUNTIFS(D2:D,"nudge_click",J2:J,"ab-a")/COUNTIFS(D2:D,"nudge_view",J2:J,"ab-a")` — 킥오프 목표 열람률 60%, 두 그룹 차이 20%p
- 참석 행사 의견 비율: 개강총회·MT(`tx` 가 TX-001 또는 TX-004)에 `opinion_submit` 을 남긴 서로 다른 vid ÷ `page_view` role=member 인 서로 다른 vid
- 총무의 불일치 거래 펼침 비율: `ui_click` act=`rowopen`, role=treasurer, target 이 TX-003·TX-004·TX-005 이고 그 vid 가 `page_view` role=treasurer target=`ab-a` 를 남긴 서로 다른 vid ÷ `page_view` role=treasurer target=`ab-a` 인 서로 다른 vid. 펼침 기록의 target 은 거래 번호라 그룹 표시가 없어서 같은 vid 의 `page_view` 로 그룹을 붙인다

읽을 때
- `ab-a`·`ab-b` 는 2026-11-08 판이 배포된 뒤의 기록에만 붙는다. 그 전 문구 A/B 기록(`nudge-claude`·`nudge-general`, `ui_click` act=`attenddone`)은 화면 조건이 달라 이 비교에 넣지 않는다.

## 사용자 테스트 피드백 반영(2026-11-07): 접힌 거래 목록 · Q&A 알림

받은 피드백은 네 가지였다. 내역이 기본으로 접혀 있으면 좋겠다, 글이 전반적으로 잘 안 읽힌다, 거래내역 등록·정리·확인이 제일 중요하다, Q&A가 들어오면 알림이 왔으면 좋겠다. 그래서 거래 내역을 달별로 묶어 한 줄씩 접고(누르면 펼침), 결제 근거 카드는 결론 한 줄을 맨 위에 두고 영수증·총무 메모·공개 Q&A를 접었다. 헤더에는 종 아이콘과 숫자를 붙였다. 아래 값으로 이 변경이 쓰이는지 본다. 대시보드의 "피드백 반영 기능" 구역에 같은 계산이 들어 있다.

| 이벤트 | 남는 열 | 뜻 |
|---|---|---|
| `ui_click` act=`rowopen` / `rowclose` | target=거래 ID | 거래 내역의 한 줄을 펼침 / 접음. 펼치면 그 거래가 선택된다(예전 카드 선택 `pick` 을 대신함) |

| `noti_click` | 같음 | 알림 목록에서 한 줄을 눌러 그 질문으로 감. `ui_click` 으로 또 남기지 않는다 |
| `ui_click` act=`answergo` | target=질문 ID | 총무 관리의 [답변하러 가기] |

수식(아직 실제 시트에서 돌려 보지 않았다)
- 펼친 사람 비율: `=COUNTUNIQUE(FILTER(B2:B, D2:D="ui_click", I2:I="rowopen"))/COUNTUNIQUE(FILTER(B2:B, D2:D="page_view", RIGHT(H2:H,6)="ledger"))`
- 영수증 칸을 연 비율: 분자를 `I2:I="unfold", J2:J="evi-receipt"`, 분모를 `RIGHT(H2:H,8)="evidence"` 로 바꾼다. 높게 나오면 영수증을 다시 위로 꺼내는 것을 검토한다.
- 알림 누름 비율(새 질문): `=COUNTIFS(D2:D,"noti_click",J2:J,"question")/COUNTIFS(D2:D,"noti_view",J2:J,"question")`. 답변은 `answer` 로 바꾼다.

읽을 때
- 알림은 서버 없이 같은 브라우저 안에서만 보인다. 총무에게는 아직 답하지 않은 질문, 부원에게는 그 브라우저에서 남긴 내 질문(localStorage `myQs`)의 답변이다. 그래서 질문한 사람과 알림을 받는 사람이 같은 경우가 많고, 질문부터 답변까지 걸린 시간은 잴 수 없다. 실서비스에서는 휴대폰 알림(앱 푸시·알림톡)으로 보낸다. 휴대폰 알림 권한은 요청하지 않는다(다크패턴 점검 a4).
- `noti_view`·`noti_click` 은 수집기 버전 4(2026-11-07 20시 45분)부터 시트에 들어온다. `ui_click` 은 원래 받던 이벤트라 그 전부터 들어왔다.
- 2026-11-07 전의 `ui_click` act=`pick` 은 예전 카드 선택이라 펼침과 섞지 않는다.
- 글 읽기 쉬움(14px 이상, 단어 중간 줄바꿈 없앰, 낱말 정리)은 기록으로 잴 수 없다. 다음 사용자 테스트에서 같은 과제("동아리방 간식 지출이 왜 문제인지 찾아보세요")에 걸린 시간과 "글이 잘 읽혔다"(5점)를 바꾸기 전 결과와 비교한다.

## 여러 명이 동시에 보낼 때(2026-11-06 시험)

실제 수집 주소로 가짜 방문자를 동시에 보내 시험했다. 시험 행은 끝난 뒤 모두 지웠다.

| 시험 | 고치기 전(수집기 버전 2, 5초마다 보냄) | 고친 뒤(버전 3, 20초마다 + 재시도) |
|---|---|---|
| 30명이 동시에 한 번 | 600행 중 360행만 남음 | 600행 모두, 한 번씩 |
| 60명이 동시에 한 번 | 하지 않음 | 600행 모두. 늦은 것은 1분 45초 뒤에 들어옴 |
| 30명이 계속 사용(4~5회) | 750행 중 455행만 남음 | 600행 모두, 한 번씩 |

- 수집기는 시트에 한 번 쓰는 데 0.5초 남짓 걸리고 한 번에 하나씩만 쓴다. 초당 1.5건 안팎이 한계다.
- 고치기 전에는 두 가지 이유로 기록이 조용히 빠졌다. 10초 안에 차례가 오지 않으면 거절했는데 앱이 다시 보내지 않았다. 잠금을 풀기 전에 시트에 확정하지 않아, 다음 요청이 같은 줄을 덮어쓴 경우도 있었다('받았다'고 답한 묶음 121개 중 2개).
- 지금은 수집기가 30초까지 기다리고, 시트에 확정한 뒤 잠금을 푼다. 앱은 20초마다(또는 30개가 쌓이면, 화면을 닫거나 가릴 때) 묶어 보내고, 'ok'를 받지 못하면 5·10·20…초, 최대 1분 간격으로 같은 묶음을 다시 보낸다. 보내지 못한 묶음은 브라우저(localStorage)에 남겼다가 다음 방문 때 보낸다.
- 수집기는 같은 묶음 이름표(bid)를 6시간 동안 한 번만 쓴다. 시험 중 응답이 늦어 다시 보낸 묶음도 한 번만 들어갔다.
- 그래서 많이 몰리면 기록이 늦게 들어올 뿐 빠지지 않는다(60명이 동시에 열면 1~2분). 다만 화면을 닫은 뒤 다시 오지 않는 사람의, 닫을 때 보낸 마지막 묶음까지 거절되면 그 묶음은 빠진다.
- 시트의 행 순서는 도착 순서라 여러 사람의 행이 섞인다. 사람별로 볼 때는 vid로 거르고 t로 정렬한다. t는 각자 기기의 시계다.
- GA4는 구글 서버가 따로 받으므로 이 문제와 상관없다.
- 2026-11-06 이전 기록(실제 이용자 201행)은 몰림이 적은 때라 크게 빠지지 않았을 것으로 보지만, 빠진 행은 흔적이 남지 않아 확인할 수 없다.

## 이 테스트로는 잴 수 없는 것

- **학기 유지율 70%** — 한 학기 동안 같은 사람이 남아 있는지는 학기가 끝나야 안다. 지금은 첫 주와 마지막 주에 다시 온 vid 비율 정도만 대신 볼 수 있다. 대시보드의 "재방문율" 카드는 서로 다른 sid 가 2개 이상인 vid ÷ 전체 vid 이다. sid 는 브라우저 탭마다 새로 생기므로 같은 날 탭을 두 개 연 것도 재방문으로 잡힌다.
- **가입자 중 월 응답 10%** — 매달 반복해서 응답한 비율이라 한 번 하는 테스트로는 나오지 않는다.
- **실제 결제·실제 쿠폰 사용·실제 광고 매출** — 목업이라 말한 의향만 있다. 의향은 실제보다 높게 나오는 경향이 있으니 모델에 넣을 때 보수적으로 깎아 쓰고, 깎은 근거를 같이 적는다.
- **CAC 단계별 전환(40/46/36%)** — 광고 집행 전이라 비어 있다. 유입 경로(src)별 가입 전환과 추천(공유) 채널의 공유 → 유입 → 참여 정보 입력까지만 볼 수 있다. 공유로 온 사람이 실제로 자기 동아리에 들여왔는지는 알 수 없다.
- **Q&A 알림의 실제 효과·답변까지 걸린 시간** — 시연은 서버 없이 한 브라우저 안에서 역할을 바꿔 쓰므로 다른 사람의 휴대폰에 알림이 가지 않는다. 알림을 본 뒤 눌렀는지(`noti_click` ÷ `noti_view`)까지만 볼 수 있다.
